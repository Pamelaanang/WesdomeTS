# Progress Report — 2026-09-14 to 2026-09-15

## Session Summary

Two arcs, picking up from the previous report's open thread. First, closing out the **Contract Code / Miner Level classification** design (flagged as open, not started, in `docs/progress_2026-09-05_to_2026-09-14.md`): a real many-to-many `MinerLevel`↔`Contract` model, editable from both the Contract-Cost Center page and the Crew Grid, used to make the Ops Sheet's Contract field Superintendent-derived instead of Shifter-editable. Second — the larger piece — turning the Crew Grid into the Superintendent's single "flip board" for every placement decision, temporary or permanent: filling a vacant basket, promoting or demoting between Miner and Shifter, transferring a basket outright, and real basket-level coverage tracking for someone temporarily standing in while the actual shifter is away. Along the way, a deliberate line was drawn and confirmed: account creation (onboarding) stays a System-Admin/IT-only function; the Superintendent owns everything about *where* an already-provisioned person sits, permanently or temporarily.

Everything below was verified with a throwaway `timesheets/order_check_test.py` `TestCase` per stage (fake data, isolated test DB), deleted once green, followed by the full suite and a real-data read-only smoke check — nothing was tested by writing to the real dev database outside of migrations and the seed command.

## 1. Contract Code / Miner Level classification

**Why:** `User.contractid` existed but was populated for zero real users; Level and Contract Code needed to be visible and editable on the Crew Grid, and — once that existed — the Ops Sheet's Contract field needed to stop being something a Shifter could accidentally reassign.

**What we built:** A real `MinerLevel` reference model (Lead/1/2/3/4, seeded via `seed_miner_levels`) and `Contract.levels` (`ManyToManyField`, mirroring the pre-existing `Contract.series` pattern) — confirmed genuinely many-to-many, not a simple one-to-one field, per direct correction: "1 contract can have multiple levels and one level can belong to multiple contracts." Contract-Cost Center page gained Level pills alongside the existing Series pills. Crew Grid gained an Edit Level/Contract modal (`edit_employee_level`), contract choices filtered by the selected level with unclassified contracts always included. Ops Sheet's `add_row`/`edit_row` now derive `contractid` server-side from the employee's live `User.contractid` whenever it's set — ignoring the posted value entirely — with the field disabled client-side and an "Assigned by Superintendent" note; only employees with no assigned contract yet keep the old open picker. `new_ops_sheet`'s auto-create-crew-rows logic prefers the live assignment over historical data and blanks the carried-forward Account when the resolved contract has changed.

**Redundancy audit (explicitly requested before building):** of three "narrow the Contract/Account choices" mechanisms that would have stacked on the same form, only one was genuinely superseded. Prior-entry-based Contract prefill became unnecessary once `User.contractid` is the live authoritative source and was removed; the Contract→Account cascade and the new Level→Contract filter answer different questions and both stayed.

**Effect:** A Shifter can no longer accidentally reassign a crew member's contract; that's now exclusively a Superintendent action, matching how the business actually works. No leftover redundant prefill logic.

## 2. Miner Level badge for Shifters + relaxed edit gate

**Why:** `'Staff'` was already a valid `minerlevel` value, but the badge (and its edit action) only appeared for Miners — a Shifter who'd been promoted up from the Miner ranks (and kept their `minerlevel`, since promotion never touches it) had no visible or editable classification anywhere on the grid.

**What we built:** The same badge now renders in the Grid's Shifter row; `edit_employee_level`'s role gate widened from Miner-only to Miner-or-Shifter.

**Effect:** dual Miner-level/Shifter-role status is visible and editable wherever it applies, not just for Miners still occupying a position row.

## 3. Vacant baskets — schema foundation

**Why:** `CrewAssignment.shifter` was a required field on every roster row, so a basket had no way to lose its shifter (via promotion, demotion, or transfer) without those roster rows either dangling on a person who's no longer a Shifter or being force-ended, hiding real crew members who hadn't gone anywhere.

**What we built:** `shifter` made nullable (migration `0021`). The Grid stopped blanking a basket's entire roster display whenever there's no shifter — existing occupants still render, just without the interactive Replace/Move controls (which route through a shifter-scoped page that doesn't exist for a leaderless basket). The "Needs Attention" panel got the same guard.

**Effect:** the schema everything else this session sits on. A basket can now genuinely go leaderless, visibly, without losing its crew.

## 4. Assign / Promote / Demote — permanent and temporary placement

**Why:** with vacant baskets representable, the Superintendent needed real ways to both fill one and permanently reclassify someone's role, without that expanding into account-creation authority.

**What we built:** `assign_basket` now claims any orphaned roster sitting on the target basket, and also permits an already-busy Shifter to pick up a second, currently-leaderless basket (previously hard-blocked — mirrors the "hold two baskets via Transfer" pattern that already existed). New `promote_to_shifter_permanent` (Miner → Shift Coordinator, `minerlevel` defaults to Staff, open to any Miner — this isn't an emergency fill, so no Lead/1/2 floor) and `demote_to_miner_permanent` (Shifter → Underground Mine Operator, **vacates rather than disperses** — nulls `shifter` on active roster rows, crew stays exactly where it is) on Shifter/Miner Management, each its own explicit confirm()-gated button, never a drag gesture.

**Effect:** every temporary and permanent placement lever exists, cleanly separated from account creation (System Admin/IT keeps that, confirmed as a deliberate authority boundary, not an oversight).

## 5. Crew Grid — the central flip board

**Why:** once vacant baskets and permanent promotion/demotion existed as real mechanisms, the explicit next step was making the Grid the single place the Superintendent does all of this, rather than bouncing between it, Shifter/Miner Management, and Crew Coverage.

**What we built:**
- **Fill This Basket** modal (click "Unassigned") — 3 radio options with plain-language descriptions, refined over several rounds specifically to reduce confusion about which button does what: *Assign an Existing Shifter*, *Promote a Miner — Temporary* (Spare Shifter, Lead/1/2 only), *Promote a Miner — Permanent* (any Miner).
- **Manage This Basket** modal (click the shifter's own name, now clickable — the standalone Transfer icon was removed from the cell since it lives here now) — 2 radios: **Transfer** (existing shifter or promote a Miner *permanently* — a one-way handoff) and **Start Coverage** (existing shifter or promote a Miner *temporarily* — the current shifter keeps nominal ownership and resumes automatically when coverage ends). The split was deliberately drawn so permanent promotion only ever happens through Transfer or Fill-This-Basket, never Coverage.
- **Real basket-level Coverage.** `CrewCoverage` gained `crewid`/`shiftertype` fields recording exactly which basket is covered (closing an ambiguity that would otherwise exist for a shifter running two baskets at once). Starting coverage moves the basket's active roster onto the covering shifter *in place* — never ending/recreating rows the way Transfer does — without touching the home shifter's own crew/section fields, so they remain the basket's nominal owner. Ending coverage (from the Grid, or from the Crew Coverage page — both now go through the same updated logic) hands the roster straight back and reverts the covering Spare Shifter to Miner if they've nothing else active, reusing a guard that already existed there.
- **Grid display fix:** `shifters_by_basket` now prefers live roster data over a shifter's static home fields whenever they disagree — the only way a covered basket actually shows the covering person instead of the nominal home owner. Never disagrees outside the coverage case, so this is a pure correctness fix.
- Demote stayed its own separate icon in the cell — deliberately not folded into the name-click modal, since it doesn't pick a destination person the way Transfer/Coverage do.

**Redundancy caught before building:** an initial 3-radio proposal (Temporary / Permanent / Transfer), each describing 2-3 scenarios, collapsed on inspection to exactly 3 real mechanisms — several of the 9 originally-described scenarios were the identical action under different narration (e.g. "temporarily assign an existing shifter" and "transfer to an existing shifter to manage two baskets" are the same operation). Caught and resolved before any code was written.

**Effect:** the Grid is now genuinely the single surface for every placement action; Shifter/Miner Management and Crew Coverage still work standalone (nothing removed), but nothing on the Grid requires leaving it anymore.
