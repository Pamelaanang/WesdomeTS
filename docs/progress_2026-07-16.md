### 3. Payroll Processed Workflow — End-to-End Build

**Design decision:** "Departments" nav link renamed to **"Processed"** to clearly distinguish it from the Unprocessed accordion sub-item. Processed = history of paid submissions.

**Flow:** Processed → Department accordion → click employee row → employee's paid cards grouped by month.

#### New URLs (`timesheets/urls.py`)
```python
path('payroll/processed/', views.payroll_processed, name='payroll_processed'),
path('payroll/processed/employee/<str:employee_id>/', views.payroll_processed_employee, name='payroll_processed_employee'),
```

Note: `<str:employee_id>` — User PKs are strings like `EMP001`, not integers. Initially written as `<int:...>` which caused a `NoReverseMatch` 500; fixed.

#### `payroll_processed` view
Fetches all active employees who have at least one paid MainHeader in the last 6 months:
```python
six_months_ago = timezone.now() - timezone.timedelta(days=180)
employees = User.objects.filter(
    mainheader__paidat__gte=six_months_ago,
    mainheader__paidat__isnull=False,
    isactive=True
).distinct().select_related('roleid__departmentid')
```

Template uses `{% regroup employees by roleid.departmentid.departmentname as department_list %}` to group into department accordions — same pattern as `user_list.html`.

#### `payroll_processed_employee` view
Fetches one employee's paid headers in the 6-month window, annotated for card display:
```python
processed_timesheets = MainHeader.objects.filter(
    employeeid=employee,
    paidat__gte=six_months_ago,
    paidat__isnull=False
).select_related('employeeid').annotate(
    entry_count=Count('mainentry', filter=Q(mainentry__linestatus='Approved')),
    total_hours=Sum('mainentry__hoursworked', filter=Q(mainentry__linestatus='Approved')),
    date_from=Min('mainentry__startdate', filter=Q(mainentry__linestatus='Approved')),
    date_to=Max('mainentry__startdate', filter=Q(mainentry__linestatus='Approved'))
).filter(entry_count__gt=0).order_by('-paidat')
```

#### `payroll_processed.html`
Department accordions using the same `toggleDept` JS + blue header pattern as `user_list.html`. Rows are clickable via `onclick="window.location=..."` to navigate to the employee history page.

#### `payroll_processed_employee.html`
Header card: inline photo + name + role + department.  
Cards grouped by paid month using `{% regroup processed_timesheets by paidat|date:"F Y" as month_groups %}`.  
Each card links back to `payroll_unprocessed_review` so payroll can still drill into full entry detail.

### 4. Operations Daily Submission Workflow — Design Confirmed

Full design locked for the next build phase.

#### Data Model
| Table | One record per | Key fields |
|---|---|---|
| `OperationsHeader` | One per day per shift per crew | `workdate`, `crewid`, `shifterid`, `overallstatus` |
| `OperationsEntry` | One per crew member in that sheet | FK to header, FK to crew member (User), `hoursworked`, `workcategoryid`, `leavetypeid` |

#### Absent / Did Not Work
No new table. Shifter selects a `LeaveType` (Vacation, Sick, Absent, etc.) for any crew member who didn't work. Payroll sees the reason on the sheet without follow-up. Uses existing `LeaveType` table.

#### Locked to Single Date
One `OperationsHeader` per shifter per crew per date. No multi-day range like maintenance.

#### Reject → Edit → Resubmit (Same Day)
Different from maintenance (where rejection is final and a new sheet is started):
- Captain rejects → header status goes to `Rejected`
- Shifter edits the same header → status resets to `Draft`
- Shifter resubmits → status back to `Submitted`
- Captain sees it again in their inbox
- Only viable within the same day — after that the window closes

#### Approval Chain + Payment Logic
| Stage | Actor | Action |
|---|---|---|
| 1 | Shifter | Submits daily crew sheet |
| 2 | Mine Captain | Approves/rejects entries |
| 3 | Payroll | Pays approved hours after captain approval |
| 4 | Superintendent | Monthly bonus review only |

Bonus logic (Superintendent review):
- Approved hours < expected → missed pay credited + bonus paid
- Approved hours slightly over → bonus offset by overage
- Approved hours way over → no bonus

#### Crew Management
Front-end UI recommended (not just DB) — crew turnover, temp members, and crew reshuffles make manual DB management painful. Mine Captain (al=4) "My Crew" nav placeholder already exists. Build alongside the submission form.

## Architectural Decisions Recorded

| Decision | Resolution |
|---|---|
| Processed vs Departments nav label | Renamed to "Processed" — mirrors "Unprocessed" terminology, makes the distinction self-evident |
| `<str:employee_id>` in URL | User PKs are strings (EMP001-style) — always use `str` converter for employee ID URL params |
| 6-month rolling window | Query filter only (`paidat__gte=six_months_ago`) — data stays in DB forever, display window is the only constraint |
| Operations absent crew members | Use existing `LeaveType` with a "Did Not Work" / absence entry — no new table |
| Operations submission lock | One header per date per crew — no multi-day range |
| Operations rejection flow | Header is editable and resubmittable (same day) — unlike maintenance where rejection is terminal |
| Operations bonus review | Superintendent review is bonus-only, separate from captain payment approval |
| Crew management | Front-end UI to be built (not DB-only) — crew changes are frequent enough to warrant it |
