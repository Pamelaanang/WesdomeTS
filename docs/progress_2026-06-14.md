### 1. `completedat` Field Added to `MainHeader`

Added a `DateTimeField` to track when a timesheet was actually approved — separate from `submittedat`.

```python
completedat = models.DateTimeField(db_column='CompletedAt', blank=True, null=True)
```

**Why `submittedat` alone is insufficient:** A timesheet submitted in May but approved in June would appear in May's stats. `completedat` correctly attributes the approval to the month it happened.

Set in `finish_review` action in `timesheets/views.py`:
```python
header.completedat = timezone.now()
```

Existing completed records backfilled via Django shell:
```python
MainHeader.objects.filter(overallstatus='Completed', completedat__isnull=True).update(completedat=timezone.now())
```

### 6. `hasaccess` Field Added to User Model

**Problem:** Crew members (whose hours a Shifter logs) must exist in the `Employee` table so `OperationsEntry.employeeid` can reference them — but they don't log into the app. `isactive=True` is correct for them (they're employed), but they should not be able to authenticate.

**Solution — `hasaccess` Boolean field:**
```python
hasaccess = models.BooleanField(db_column='HasAccess', default=True)
```

- `isactive` = are they employed
- `hasaccess` = can they log into the application

**Login gate added** in `users/views.py`:
```python
if not user.hasaccess:
    form.add_error(None, "This account does not have application access.")
    return render(request, 'login.html', {'form': form})
```

**Future-proof:** Flipping `hasaccess=True` for a crew member later (if they get app access) immediately allows them to log in and see their own entries read-only via `OperationsEntry.objects.filter(employeeid=request.user)` — no schema or data changes needed.

Migration `users/migrations/0002_user_hasaccess.py` run successfully. Default `True` — all existing users unaffected.

### 7. Replace Employee Workflow

Built a full admin workflow for when an employee is fired/leaves and a new hire arrives.

**New view:** `replace_employee(request, employeeid)` in `users/views.py`  
**New URL:** `users/replace/<employeeid>/` → `replace_employee`  
**New template:** `templates/replace_employee.html`  
**User list:** Added red "Replace" button per active employee + improved Status column (Active / Temporary / Inactive with colour coding)

**What the flow does on submit:**
1. Creates new `User` with the entered details, same role and `supervisorid` as the departing employee, temp password generated
2. Reassigns all active subordinates: `User.objects.filter(supervisorid=leaving).update(supervisorid=new_hire)`
3. If the departing employee is a Shifter (`al=5`) and transfer checkbox is ticked:
   - End-dates all active `CrewAssignment` records for the Shifter
   - Bulk-creates new `CrewAssignment` records linking the same crew members to the new hire
4. Sets `leaving.isactive = False`

**Crew member clarification (architectural):**
- Crew members have `supervisorid=null` — their relationship to a Shifter is via `CrewAssignment`, not `supervisorid`
- When replacing a Shifter, no `supervisorid` cascade is needed — only `CrewAssignment` is touched
- This is why Shifters have no subordinates via `supervisorid` even though they manage crew operationally

### 8. Architecture — Multi-Department Superintendent Scoping (Confirmed Design)

All Superintendents share `al=2`. Their `roleid.departmentid` scopes what they see — no new access levels needed. Scales to any future department (Electrical, Safety, etc.) with zero schema changes.

**Rule established:**
- One table pair per unique data shape (not per department)
- Department scoping via `departmentid` on role, not by multiplying access levels

## Architectural Decisions Recorded

| Decision | Resolution |
|---|---|
| Superintendent cross-dept isolation | `roleid.departmentid` — no new access levels |
| Mine Captain crew visibility | Role-based pull (`al=4` + `overallstatus='Submitted'`), not FK-based |
| Crew member identity in DB | `Employee` table, `isactive=True`, `hasaccess=False`, `supervisorid=null` |
| Crew member → Shifter link | `CrewAssignment` table (with date ranges), not `supervisorid` |
| Stat holiday work category | `isproductive=1` in `WorkCategory` — data entry, no schema change |
| Future crew member app access | Flip `hasaccess=True` + assign role — OperationsEntry already attributes to individual |
