### Crew identity vs. crew membership
**Problem:** `OperationsHeader.crewid` (A/B/C/D) was a manually-picked dropdown with zero relational link to the actual roster. Roster pre-population is driven entirely by `CrewAssignment`/`CrewCoverage` via `effective_shifter`, completely independent of what crew letter was typed in. Picking the wrong one didn't corrupt data, but silently mislabeled the header for every downstream report that groups by crew.

**Root cause (confirmed with Pamela):** crew letter is an attribute of the *shifter* — fixed while they're active. Crew *membership* (who's currently under them) is separate and churns often — already correctly modeled by `CrewAssignment`. The dropdown conflated the two.

**Fix:** Added `User.crewid` (FK → `Crews`, nullable). `new_ops_sheet` no longer asks — it derives crew the same way `section` already was: own account for an own-crew sheet, `coverage.home_shifter` for a covering sheet. If that shifter's `crewid` isn't set yet, sheet creation is blocked with a clear message rather than silently mislabeling.

### Coverage dual-submission — already safe
**Question:** Can a covering shifter submit both their own crew's sheet and a covering sheet for the same shift, without them interfering?

**Confirmed (no code change needed):** `coverageid_id` is part of the existing-header uniqueness lookup, so the same shifter/date/shifttype can have two separate `OperationsHeader` rows — one with `coverageid=None`, one per `CrewCoverage`. `my_ops_sheets.html` already visually distinguishes them (crew name vs. green "Covering [Name]" tag).

### Approval routing is generic, not department-hardcoded
**Question:** Does a non-Maintenance department need its own access level to mimic "Supervisor"?

**Confirmed:** No. `business_approval_inbox`/`review_business_timesheet` gate on `access_level in [2,3,4]` and then scope purely via `subordinates = User.objects.filter(supervisorid=request.user)` — no department check anywhere. `Roles` already separates `departmentid` from `accessid`, so any department can have its own Role pointed at `accessid=3` and the exact same views/inbox work immediately. Left `approval_inbox` (the Maintenance-specific MainHeader review) hard-gated to al=3 only, since there's no current need to loosen it.

### Sheet-level contract/account default (Ops prepopulation)
**Considered:** bulk auto-creating all crew rows on sheet creation, vs. a lighter sheet-level default.

**Decision:** Rejected bulk auto-rows — `OperationsEntry.contractid`/`hoursworked` are non-nullable, so pre-creating rows risks DB errors (no contract known for someone with no history) or zero-hour ghost rows getting accidentally submitted. Instead added a sheet-level contract/account default: whatever was last saved *on that sheet* now pre-fills the Add Row form automatically, carrying forward across saves (full-page-reload architecture otherwise reset it each time). Per-person history still overrides it when more specific.

---

### `create_superuser()` bug found while planning the DB reset
**Problem:** `python manage.py createsuperuser` never actually sets `is_superuser=True` on this custom `EmployeeManager` — Django's `createsuperuser` command delegates flag-setting entirely to the manager method, and this one never did it (unlike Django's own default, which does and even raises if it's not set). Result: a "superuser" created this way could log into `/admin/` (since `is_staff` is a computed property off `access_level`) but would see zero manageable models, since Django only bypasses its permission system for `is_superuser=True`.

**Fix:** Added `extra_fields.setdefault('is_superuser', True)` plus the same validation guard Django's own implementation uses.
