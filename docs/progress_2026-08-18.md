## Questions, Corrections & Design Decisions

### Supervisor dropdown: "expected a number but received string"
**Reported:** Assigning a supervisor to a user threw a type error on save.

**Root cause:** After yesterday's migration, `User.supervisorid` is a FK to `eid` (integer PK), but the Add/Edit Employee modals' Supervisor `<option value>` was still populated from `sup.employeeid` (the string business ID) — a leftover from before the PK swap. Posting the form tried to assign a string like `"AProdS1"` to an integer FK column.

**Fix:** Both modals' Supervisor `<option>` now use `sup.eid`. Also fixed `edit_employee`'s self-supervision guard, which was comparing the posted `supervisorid` (now an eid) against `employee.employeeid` (a string) — updated to compare against `str(employee.eid)`.

### Duplicate Position rows
**Reported:** The Position dropdown (crew member position picker) showed some position names more than once.

**Investigated:** Not a query bug — `Position.objects.filter(isactive=1)` is a flat, joinless query. The `Position` table itself had genuine duplicate rows: 18 names (e.g. "Blaster", "Bolter 1", "Sill Crew") each existed as 2–3 separate active rows with different `positionid`s, most likely from a prior bulk import or manual admin entry that wasn't deduplicated.

**Fix:** Confirmed via `CrewAssignment` lookup that none of the 24 duplicate rows were referenced by any assignment, so they were safe to delete outright. Kept the lowest `positionid` per name, deleted the rest. 45 active positions → 21.

### Crew Assignment "Select Employee" dropdown — same root cause as the supervisor bug
**Reported:** "Only some miners appear in the list" when adding a crew member.

**Root cause:** `crew_assignment_detail`'s `available_employees` query excluded already-assigned miners using:
```python
assigned_ids = CrewAssignment.objects.filter(enddate__isnull=True).values_list('employee_id', flat=True)
available_employees = User.objects.filter(...).exclude(employeeid__in=assigned_ids)
```
`assigned_ids` holds `eid` integers (e.g. `9`, `10`), but the exclude compared them against `employeeid`, a **string** column. MySQL coerces strings to numbers by leading digits for that comparison — so `'9EMine'` and `'10EMine'` got wrongly excluded (they coerce to 9 and 10), while the employees who were *actually* assigned (`1EMiner`, eid=9; `2BCMine`, eid=10) stayed visible, since their ID strings don't coerce to 9/10. Confirmed directly against MySQL: `SELECT EmployeeID FROM Employee WHERE EmployeeID IN (9, 10)` returned `9EMine` and `10EMine`, not the actual eid-9/10 rows.

**Fix:** Changed the exclude to `.exclude(eid__in=assigned_ids)`. Verified: dropdown now correctly shows all 10 unassigned test miners and correctly hides the 2 who are genuinely on a crew.

### Stale project notes corrected — Ops crew "prepopulation" wasn't actually built
**Context:** Prior project notes (and my first answer this session) claimed Operations crew sheets already auto-populated a row per active crew member on sheet creation. Re-reading `ops_sheet.html` showed this was wrong: `active_assignments` was only ever used to build the "Your Crew" optgroup inside the manual **+ Add Row** form — nothing auto-created rows on page load. The per-person contract/account **prefill** (`applyPrefill()`) was real and did work once a crew member was manually selected, but the row itself was never automatic.

**Decision (confirmed with Pamela):** Build the real thing — auto-create one row per active crew member when a new sheet is created, carrying forward contract/account from each person's own most recent entry. Considered auto-creating rows for everyone including first-timers (would need a schema change, since `OperationsEntry.contractid`/`hoursworked` are `NOT NULL` and a first-time crew member has no prior contract to carry forward) — **rejected** for now; first-timers stay reachable via the existing + Add Row picker, and auto-population kicks in starting from each person's 2nd sheet onward. Guests are untouched — never auto-added, still only reachable via + Add Row, exactly as before.
